# Translation Checker — переводы TaskMan (8 языков)

## Главный принцип

Машинный перевод (Yandex API) **не знает контекста приложения**. Он не понимает, что `Image` — это
название ресурса в лимитах, а `Team` — сущность продукта, а не «отряд». Поэтому любой автоматический
перевод — это черновик, который **обязательно проходит проверку**:

1. **Механические проверки** (плейсхолдеры, теги, fuzzy, пунктуация) — их делает скрипт
   `check_po.py`, они объективны и обязательны.
2. **Смысловая верификация** — агент проверяет те языки, которые знает: `ru`, `es`, `zh-hans`.
3. **Ревью носителем** — для `az`, `ky`, `tg`, `kk` агент **не может** ручаться за грамматику
   (падежи, аффиксы, согласование). Такие строки выносятся в отдельный список для пользователя.

Никогда не выдавай перевод за проверенный, если он не прошёл все три ступени.

## Когда срабатывать

- Появились новые `{% trans %}` / `{% blocktrans %}` / `_()` в коде.
- Пользователь просит перевести строки, поправить переводы, проверить `.po`, «сделать локализацию».
- Запускается `make messages`, `make translate`, `make translate-ru`, `make translate-from-ru`, `make compile`.
- Перед коммитом, если в diff есть файлы `task_manager/locale/*/LC_MESSAGES/django.po`.
- Появились fuzzy-записи или `.po` перестал компилироваться.

## Устройство переводов в проекте

| Что | Где |
|---|---|
| Строки-источники (msgid) | `{% trans %}` в шаблонах, `_()`/`gettext_lazy` в Python |
| Каталоги | `task_manager/locale/<lang>/LC_MESSAGES/django.po` (+ скомпилированный `django.mo`) |
| Языки | `ru`, `az`, `ky`, `tg`, `es`, `zh_Hans`, `kk` (+ `en` как источник) |
| Скрипт автоперевода | `scripts/translate_po.py` (polib + Yandex Translate API) |
| Команды | `make messages`, `make translate-ru`, `make translate-from-ru`, `make compile` |
| Переменные | `YANDEX_TRANSLATE_API_KEY`, `YANDEX_FOLDER_ID` в `.env` |
| Инструмент проверки | `.agents/skills/translation-checker/check_po.py` |
| Глоссарий терминов | `.agents/skills/translation-checker/glossary.json` |

**Двухстадийный workflow** (из `README.md`): сначала EN→RU, затем RU→остальные языки.
Русский — единственный источник, который агент правит руками; он же служит источником для
`FROM_RU=1`, поэтому качество русского определяет качество всех остальных языков.

## Пошаговый процесс

### Шаг 0. Извлечь новые строки

```bash
cd task_manager && poetry run django-admin makemessages -a && cd ..
```

**Готча:** `make messages` падает с `django-admin: not found` (бинарник не в PATH вне Poetry).
Запускай `makemessages` через `poetry run` из каталога `task_manager` — иначе Django создаст
мусорный корневой `locale/`.

После `makemessages` diff по `.po` всегда большой: Django переформатирует переносы строк и
обновляет `#:` ссылки на файлы. Это нормально, но **не коммить `.po` только ради переформатирования**.

### Шаг 1. Найти проблемные записи

```bash
poetry run python .agents/skills/translation-checker/check_po.py check
```

Скрипт возвращает `1`, если есть ошибки. Ошибки блокируют компиляцию — их надо исправить все.
Разбирай уровни так:

| Уровень | Значение | Действие |
|---|---|---|
| `error` fuzzy | `msgfmt` пропустит строку → в UI останется английский | перевести заново, снять fuzzy |
| `error` битый плейсхолдер | `%(name) s`, `%(tam_name)s`, `% (max_mb)s` → падение рендера | восстановить плейсхолдер из msgid |
| `error` плейсхолдеры нет/лишние | при подстановке будет `KeyError`/пустая подстановка | вернуть плейсхолдеры msgid как есть |
| `error` HTML-теги | потерян `<strong>`, появился `<strong >` | скопировать теги из msgid |
| `error` шапка fuzzy / нет Language | `makemessages` снова пометит новые строки fuzzy | `fix-meta` |
| `warn` `#| msgid` | остался след старого перевода — строка переведена по похожему msgid, а не по своему | проверить смысл, затем убрать след |
| `warn` пунктуация | перевод потерял/добавил точку | поправить, если строка-метка или кнопка |

### Шаг 2. Перевести (EN → RU), затем проверить русский

```bash
make translate-ru      # TARGET_LANG=ru, только пустые/fuzzy
```

Затем **вручную вычитай** новый русский перевод — это ключевой шаг. Проверь:

- смысл в контексте UI (кнопка, заголовок, подсказка, письмо-уведомление, текст ошибки);
- род/число согласованы с тем, к чему относится строка (`Следующая` для страницы, не `Следующий`);
- термины совпадают с глоссарием (см. ниже) — «задача», «команда», «метка», «заметка», «статус»;
- `TaskMan` не переведён и не транслитерирован;
- плейсхолдеры `%(name)s` и `{team_name}` на месте.

### Шаг 3. Перевести остальные языки из проверенного русского

```bash
make translate-from-ru   # FROM_RU=1: ru → az, ky, tg, es, zh-hans, kk
```

Скрипт пропустит msgid, для которых нет русского перевода, и напечатает их список —
сначала закрой русские пропуски, потом повторяй.

### Шаг 4. Проверить и починить результат

```bash
poetry run python .agents/skills/translation-checker/check_po.py fix --dry-run
poetry run python .agents/skills/translation-checker/check_po.py fix --fix-meta
poetry run python .agents/skills/translation-checker/check_po.py check
poetry run python .agents/skills/translation-checker/check_po.py glossary
poetry run python .agents/skills/translation-checker/check_po.py compile
```

**Авто-починка (`fix`) — обязательный шаг после каждого автоперевода.** Yandex Translate ломает
плейсхолдеры предсказуемо, и это можно восстановить механически, не трогая остальной текст:

| Что сломано | Пример | Как чинится |
|---|---|---|
| пробел внутри плейсхолдера | `%(name) s` | склеивается в `%(name)s` |
| пробел перед скобкой | `% (max_mb)s` | склеивается в `%(max_mb)s` |
| испорченное имя | `%(tam_name)s`, `%(mx_count)s` | подбирается похожее имя из msgid (`team_name`, `max_count`) |
| пробел в HTML-теге | `<strong >` | убирается пробел |

Похожесть имён считается через `difflib` с порогом 0.75: опечатка `tam_name` → `team_name`
даёт 0.94, а разные имена (`username` vs `team_name`) — 0.59, поэтому подмена не случится.
Если имя не похоже ни на одно из msgid, `fix` его **не трогает** — такое уходит в отчёт `check`.

**Порядок плейсхолдеров `fix` намеренно не меняет.** В проекте нет позиционных `%s`/`%d`
(проверено по всем 7 языкам — 0 вхождений), все плейсхолдеры именованные, подстановка идёт
по имени. А порядок слов в казахском, киргизском или таджикском может отличаться от английского,
и перестановка сломала бы грамматику. `check` по той же причине не считает другой порядок ошибкой.

Всегда сначала смотри `--dry-run`, затем применяй. `--fix-meta` заодно нормализует шапку файла.

`compile` прогоняет `msgfmt --check-format` по каждому языку. `compilemessages` возвращает
`exit 1`, если в файле битые плейсхолдеры, — обязательно убеждайся, что он проходит **до** коммита.

### Шаг 5. Сверить смыcл по языкам

- `ru`, `es`, `zh-hans` — вычитай сам, строка за строкой (грамматика, регистр, термины).
- `az`, `ky`, `tg`, `kk` — проверь только механику и терминологию, а спорное вынеси в список
  для носителя (шаг 6).

### Шаг 6. Список для ревью носителем

Для языков, где агент не уверен, выгрузи таблицу и передай пользователю:

```bash
poetry run python .agents/skills/translation-checker/check_po.py export kk --out /tmp/kk-review.md
```

В отчёт включай **только новые и изменённые строки**, а не все 500+:
сначала `git diff` по нужному `.po`, затем `export` с `--filter` по ключевому слову, либо
отфильтруй таблицу по строкам из diff.

Что помечать как «требует носителя»:

- казахский: падежные аффиксы (`-ға/-ге/-да/-де`), притяжательные формы, порядок слов;
- киргизский: аффиксы сказуемости, согласование по лицу;
- таджикский: изафетные конструкции, послелоги;
- азербайджанский: аффиксы принадлежности, `-ın/-in/-un/-ün`.

Формат отчёта пользователю — таблица `| EN | RU | <язык> |` + короткое пояснение, почему строка
сомнительная. В конце перечисли, какие языки ты проверил полностью, а какие отдаёшь на ревью.

### Шаг 7. Компиляция

```bash
make compile   # django-admin compilemessages
```

`.mo` закоммичены в репозиторий — обновляй их вместе с `.po`, иначе изменения не попадут в UI.
Правки переводов — это **patch** по правилам `semver-checker`.

## Глоссарий

`glossary.json` фиксирует, как называются сущности продукта на каждом языке. Файл подтверждён
пользователем как источник истины; проверка:

```bash
poetry run python .agents/skills/translation-checker/check_po.py glossary
```

Термин переводится **одинаково во всём UI**. Формат значения — варианты через `|`
(`"ru": "задач|задач"`, `"es": "etiqueta"`), проверка ищет любой из вариантов как подстроку
без учёта регистра.

Уже найденные расхождения в текущих файлах:

| Термин | Правильно | Ошибки в файлах |
|---|---|---|
| task | `es` tarea | `es`: `Nuevo reto` для `New task` |
| team | `es` equipo | `es`: `comando` в 20+ строках (это «команда» как приказ) |
| member | `es` miembro | `es`: `Participante` в части строк |
| image | `zh-hans` 图片 | `zh-hans`: `图像` в части строк |

Найденные расхождения — **не повод молча их переписать**: предложи пользователю починку
отдельным коммитом, потому что это правка существующего поведения.

Если появляется новая сущность продукта (например «изображение» в казахском), сначала добавь
термин в `glossary.json`, потом переводи — иначе согласованность ничем не удержится.

## Исправление fuzzy

fuzzy бывает двух видов, и лечить их надо по-разному.

1. **Fuzzy в шапке файла** (`#, fuzzy` над `msgid ""`). Возникает, когда в шапке пустой `Language:`.
   Django при каждом `makemessages` помечает fuzzy все новые строки, если шапка не «настроена».
   Лечится один раз:

   ```bash
   poetry run python .agents/skills/translation-checker/check_po.py fix-meta
   ```

   Команда заполняет `Language`, `Language-Team`, `Last-Translator`, `PO-Revision-Date` и снимает
   fuzzy с шапки. После этого `makemessages` больше не плодит fuzzy на новых строках
   (проверено: с заполненным `Language` fuzzy не возвращается).

2. **Fuzzy на записи** (`#, fuzzy` + `#| msgid "..."`). Это перевод **другой, похожей** строки,
   который `makemessages` подставил автоматически. Пример из `ru`: `note images` получил
   `Вставить изображение` (от `Insert Image`), `Simplified Chinese` — `Упрощённый вид` (от `Simple view`).
   Такой перевод чаще всего неверен по смыслу. Действия:
   - перевести строку заново (её подхватят `make translate-ru` / `make translate-from-ru`,
     потому что fuzzy-записи считаются непереведёнными);
   - снять `fuzzy` и очистить `#| msgid`, иначе `msgfmt` выкинет перевод из `.mo`
     (проверено: fuzzy-строка в `.mo` не попадает, в UI остаётся английский).

Массово применить готовые переводы можно из JSON:

```bash
poetry run python .agents/skills/translation-checker/check_po.py apply fixes.json --dry-run
poetry run python .agents/skills/translation-checker/check_po.py apply fixes.json
```

Формат файла: `{"kk": {"Zoom in": "Үлкейту"}, "ru": {"Zoom out": "Уменьшить"}}`.
Команда снимает fuzzy и `#| msgid` у применённых строк.

## Починенная проблема скрипта автоперевода (30.09.2026)

Раньше `PLACEHOLDER_RE` в `scripts/translate_po.py` ожидало `[sd]` перед закрывающей скобкой
и **не находило** `%(name)s`. Из-за этого плейсхолдеры уходили в Yandex обычным текстом и
возвращались поломанными (`%(name) s`, `%(mx_count)s`, `%(tam_name)s`), а
`verify_placeholders()` поломку не замечал и не помечал строку fuzzy — битый перевод попадал
в `.mo` и ломал рендер страницы.

Исправлено (ветка `feature/i18n-fixes`):

- паттерн приведён к виду `%\([A-Za-z_][A-Za-z0-9_]*\)[sd]|%[sd]|\{[A-Za-z_][A-Za-z0-9_]*\}`,
  то есть теперь закрывает и `%(name)s`, и `%s`, и `{brace}`-плейсхолдеры
  (последние раньше не экранировались вообще);
- маркер `__PH0000__` теперь несёт индекс плейсхолдера, поэтому маркер, переставленный
  переводчиком, получает **свой** плейсхолдер, а не соседний по порядку;
- перед восстановлением проверяется число маркеров: если API потерял или продублировал
  маркер, запись помечается fuzzy и уходит на ручной перевод;
- в `.po` теперь пишется **восстановленный** текст. Раньше `_apply_single_translation()`
  возвращала только флаги, а `_apply_translations()` сохраняла сырой ответ API — то есть
  маркеры `__PH0000__` попадали прямо в файл, а `verify_placeholders()` проверял текст,
  который никуда не шёл;
- при несовпадении плейсхолдеров запись помечается fuzzy (проверка `needs_fuzzy` идёт
  **до** проверки `success`, иначе битый перевод оставался невалидным и не fuzzy);
- `_get_available_langs()` нормализует имя каталога `zh_Hans` в код `zh-hans`, поэтому
  `FROM_RU=1` и режим по умолчанию больше не пропускают китайский (`show_untranslated()`
  и `list` тоже ходят по правильному пути).

Регрессия закрыта тестами `tests/test_translate_po.py` (19 тестов: паттерн, round-trip
маркеров, перестановка маркеров, запись восстановленного текста, fuzzy при сбое API,
нормализация `zh_Hans`).

`check_po.py` остаётся **обязательным** после каждого автоперевода: он ловит не только
плейсхолдеры, но и fuzzy, теги, пунктуацию и терминологию.

## Команды инструмента

```bash
check_po.py check [--langs ru es] [--show-info] [--no-fail]  # отчёт по проблемам
check_po.py fix [--langs es kk] [--dry-run] [--fix-meta]      # авто-починка плейсхолдеров
check_po.py fix-meta [--langs es kk]                          # нормализовать шапки
check_po.py glossary [--langs es zh-hans]                     # согласованность терминов
check_po.py export <lang> [--filter Слово] [--out file.md]     # таблица EN|RU|lang для ревью
check_po.py apply <file.json> [--dry-run]                      # применить переводы, снять fuzzy
check_po.py compile [--langs kk]                               # msgfmt --check-format
```
