# Semver Checker — проверка версии перед коммитом (TaskMan)

## Когда срабатывать

При любом запросе на коммит: «закоммить», «сделай commit», «зафиксируй изменения», «commit», «подготовь коммит» и т.п. **До** формирования сообщения коммита и выполнения `git commit`.

## Что делает навык

1. Анализирует изменения (`git diff`) и определяет тип semver-бампа.
2. Если бамп нужен — обновляет версию в `pyproject.toml`.
3. Включает информацию о версии в сообщение коммита.

## Шаг 1: Сбор информации

Выполни параллельно:
- `git diff --staged` — если есть staged-изменения (предпочтительно).
- `git diff HEAD` — если staged пуст, но есть unstaged-изменения.
- Прочитай текущую версию из `pyproject.toml` (строка `version = "x.y.z"`).

## Шаг 2: Определение типа изменения

Проанализируй файлы и характер изменений в diff. Используй следующие правила:

### Major (x.0.0)
- Переход на новую архитектуру или фундаментальное изменение стека технологий.
- Удаление существующей функциональности, на которую опираются пользователи.
- Несовместимые изменения API, моделей данных или формата БД (миграции, ломающие обратную совместимость).
- Изменения, требующие ручной миграции данных у существующих инсталляций.

### Minor (x.y.0)
- Новые функции, новые страницы, новые эндпоинты.
- Существенное расширение возможностей (новые поля моделей с миграциями, новые статусы, новые типы уведомлений).
- Обратная совместимость сохранена.

### Patch (x.y.z)
- Исправление багов.
- Небольшой рефакторинг.
- Обновление зависимостей.
- Улучшение UX без новой функциональности.
- Изменения переводов/локалей без новой функциональности.
- Правки дефолтных значений, цветов, текстов.

### None (версия не меняется)
- Только документация (README, KODA.md, CONTRIBUTING.md, комментарии).
- Только тесты.
- Только CI/CD конфигурация (.github/workflows).
- Только форматирование/стиль кода без логических изменений.
- Изменения в `.gitignore`, линтер-конфигах, `sonar-project.properties`.
- Docker-файлы без изменений зависимостей.

**Важно:** Если сомневаешься между minor и patch — выбирай patch. Между major и minor — выбирай minor. Бамп major должен быть обоснованным.

## Шаг 3: Обновление версии (если бамп нужен)

Если тип изменения — не `none`, вычисли новую версию и обнови `pyproject.toml`:

| Файл | Что менять | Формат |
|---|---|---|
| `pyproject.toml` | `version = "x.y.z"` | Строка в кавычках |

**Это единственное место с версией в проекте.** Приложение читает её из `pyproject.toml` через `task_manager/settings.py` (`VERSION = tomllib.load(...)['tool']['poetry']['version']`) и показывает в футере (`base.html` → `{{ VERSION }}`) и использует для кеш-бастинга статики (`STATIC_VERSION` в `context_processors.py`).

**`poetry.lock` трогать не нужно**: в Poetry 2.x content-hash не зависит от версии проекта. Обновляй lock только если в коммите менялись сами зависимости.

## Шаг 4: Проверка согласованности

После обновления перечитай `pyproject.toml` и убедись, что версия корректна. Запусти `poetry run python -c "import tomllib; print(tomllib.load(open('pyproject.toml','rb'))['tool']['poetry']['version'])"` для проверки.

## Шаг 5: Информация в сообщении коммита

Включи в сообщение коммита (в конце, после основного описания) строку:

```
Bump version: 2.27.11 → 2.28.0 (minor)
```

Если версия не менялась — ничего не добавляй.

## Пограничные случаи

- **Версия уже обновлена в diff**: Если в diff уже есть изменение версии в `pyproject.toml` — не дублируй обновление, но проверь, что тип бампа соответствует характеру изменений.
- **Несколько коммитов подряд**: Каждый коммит анализируется независимо. Если предыдущий коммит уже сделал minor-бамп, а этот — patch-фикс, бампай patch от новой версии.
- **Pre-release**: Если текущая версия содержит суффикс (например `1.0.0-rc.1`), учитывай его при вычислении новой версии.
- **Мерж PR из ветки с несколькими коммитами**: Squash-merge считается одним изменением — бамп по суммарному diff.
